## 终态结论

**T10 兼容性策略的九条纪律**

策略实现在 `packages/charts-core/src/engine/compatibility.ts`，测试 `tests/unit/sdk-compatibility.test.ts` 共 **51 例**（20 → 33 → 41 → 51，四轮扩展，每轮都留下先红后绿的用例）。九条纪律跨 0.0.8 / 0.0.9 / 0.0.10 三轮修复确立（`t10-sdk-compatibility.md` 第八、九节 + `t10-a-to-b-interface-handover.md`）：

1. 探针收到的 `combination.echartsVersion` 是**候选**版本，不是基线版本（0.0.8）；
2. 覆盖判定按**精确组合**一一对应（框架 + 框架版本 + ECharts 基线），少一条、多一条、重复一条、版本写错一条都 `hold`（0.0.8）；
3. **混合 ECharts 基线直接拒绝出报告**，且拒绝与数组顺序无关（0.0.8）；
4. 逐行核对实际验的 `echartsVersion` 必须等于 `report.candidate.version`，篡改任一行不放行（`9679bac`，0.0.9）；
5. **`supported` 是唯一事实来源**：`recommend` 只用 `supported` 的唯一 ECharts 基线推导 peer 符合性并核对 `report.baselineEchartsVersion` 精确等于它；报告里的 `peerSatisfied` 只是转述，伪造 `true`/`false` 都不影响判定（`b901dc4`，0.0.10）；
6. `supported` 必须同时覆盖 Vue 与 React（用框架集合判定而非计数），单框架齐验一律 `hold`（0.0.10）；
7. `baselineEchartsVersion` 自 0.0.9 起为**可选**（0.0.8 曾设为必填、那对公开类型是破坏性变更却按 PATCH 发版，是「必填字段=破坏性变更」的教训），**缺失即 fail-closed**（`hasDualFrameworkCoverage` 为 `false`、`recommend` 为 `'hold'`）；
8. `supportedRangeUnchanged` 恒为 `true`，结构上堵死自动扩范围；
9. 报告不得包含「建议的新支持范围」，扩范围是人的决定。

候选结论：`echarts@6.1.0` = supported 唯一基线 = 官方 `latest`（「无新上游版本」分支成立，因此跨版本升级矩阵始终未完成）；**`echarts@6.0.0` 结论恒为 `hold`**——严格 peer 安装被 `ERESOLVE` / `PROBE_PEER_REJECTED` 拒绝（安装层最硬证据：任何代码都不会跑起来），放宽后类型/运行/交互双框架通过但 `skipLibCheck: false` 下存在类型静默降级（`ComposeOption`、`BarSeriesOption` 等 `TS2305`），且无 6.0.0 截图基线。0.0.11/0.0.12 世代仍保持该结论（`sdk-label-clipping-repair-2026-11-16.md`、`sdk-label-adopt-acceptance-2026-11-16.md` 复现：四条 strict/strict-only 路径 exit 1 / `PROBE_FAILED`，内层 `PROBE_PEER_REJECTED`；显式 legacy 只测量不采用）。`peerDependencies.echarts` 始终保持 `6.1.0` 未扩大。

回退目标：只能是 `0.0.10`（当时当前）或 `0.0.6`（末次全图验收）；**不要回退到 0.0.7 / 0.0.8 / 0.0.9**（0.0.7 有三个 Important 策略缺陷、0.0.8 引入必填字段破坏公开类型、0.0.9 有基线与单框架遗漏）。已发布版本不可变，同名同版本不同摘要报 `CONFLICT` 失败关闭。

一份贯穿全主题的失败模式：多轮缺陷的共同点是「报告自称验证了某件事、实际验的是另一件事」（探针收到基线、覆盖只按框架、基线取首项、篡改实测行、伪造 `peerSatisfied`、报告基线未绑定 `supported`、单框架齐验、字体摘要覆盖不一致、脏消费者复制）。所有修复的方向都是**把判据绑到外部事实来源**（`supported`、消费者 `package-lock.json`、`node_modules` 真实版本、真实测量的字体指纹）。

**混合版本三闸门（CLI 0.0.10 无法对 core 0.0.10 + vue/react 0.0.11 跑 56 组合的解剖）**

由 `b-installed-probe-next-2026-11-16.md` 只读审计定位、`a-t10-strict-handoff-2026-11-16.md` 先行回报第一处：

- 闸门 1（CLI 自身，最先触发，B 所有权）：`packages/component-cli/src/commands/echarts.ts:317-323`（tarball 内 `dist/commands/echarts.js:169-173`）为 `if (packageVersions.size !== 1) return { ok: false, errorCode: 'INVALID_BUNDLE_MANIFEST', error: ... };`（文案「冻结 bundle 三个包版本必须一致，当前为: ...」）。`checkEchartsBundle` 与 `verifyEchartsCandidate` 都在第一步调用 `readAndVerifyFrozenBundle`，因此 check 与 verify 都在这里失败，探针不会启动，也不会访问网络。B 沙箱复现输出 `{ "ok": false, "errorCode": "INVALID_BUNDLE_MANIFEST", "error": "冻结 bundle 三个包版本必须一致，当前为: 0.0.10, 0.0.11" }`；C 宿主实测已安装 CLI 0.0.10 的 `echarts check` / `verify` 两次均为 exit 1 / `INVALID_BUNDLE_MANIFEST`，直接调用包内 `readFrozenBundle` 得到 `PROBE_INPUT 版本不一致`，浏览器矩阵未启动。

- 不会触发的闸门（已核实，排除误判）：`MIXED_PEER_BASELINE`（`echarts.ts:325-331`）不触发（三包 echarts peer 集合大小 1）；探针对 charts-core 的依赖版本校验（`bundle.mjs:104-108`）通过；三包 tarball 摘要/字节校验通过；额外诊断文件（如 `acceptance.json`）在此 echarts 路径不读取（完整发布目录校验 `verifyReleaseBundle` 会拒绝原目录的额外文件，故本轮使用 C 已严格核验的声明材料副本，不能据此放宽发布校验）；`workspace:` 协议残留无。

**探针体系终态与分发合同**

- 探针位置与两种形态：源码在 `tests/acceptance/t10-sdk/`（7 个模块 + `probe.test.mjs`）；分发形态由 `packages/component-cli/scripts/package-probe.mjs` 打成 `packages/component-cli/dist/probe/`（8 模块 + `probe.test.mjs` + `probe-manifest.json` + `resources/`，**73 个文件**，逐文件白名单 + 双向判据 + 无过滤复核 + 删除前三判闸门）。
- 四维口径（不新增第五维）：`typecheck` / `runtime` / `interaction` / `visual`；`not-run` 永远保持 `not-run`；`uncovered`（本地本该跑而没跑、参与门禁）与 `scopeNotes`（范围声明、仅供阅读）严格分工。
- `environmentKey = SHA-256(环境投影规范化 JSON)`，**不含** `frameworkVersion` 与 `echartsVersion`；同环境同字节才判 `PASS`，环境签名不同判 `INCOMPATIBLE`；`unknown-manual` 来源不得参与自动基线比对。审计器 `scripts/audit-t10-evidence.mjs` 不接受操作者覆盖字体摘要，默认检查双框架共 **56 个组合**（Windows / Node 26.13.0 / Chromium revision 1254 / 实测字体）。
- 退出码：探针 `0` 跑完（**不等于 adopt**）/ `1` 探针失败或输入非法 / `2` `--fail-on-hold` 且 hold。CLI 侧另有 `PROBE_HOLD` / `PROBE_FAILED` / `INCOMPLETE_EVIDENCE` / `POLICY_NOT_SATISFIED` / `INVALID_PROBE_EVIDENCE` / `BUNDLE_EVIDENCE_MISMATCH` / `CANDIDATE_MISMATCH` / `CANDIDATE_INTEGRITY_MISMATCH` / `CANDIDATE_SOURCE_MISMATCH` / `CANDIDATE_INTEGRITY_UNVERIFIED` / `FRAMEWORK_COVERAGE_INVALID` / `FRAMEWORK_VERSION_MISMATCH` / `OFFLINE_VERIFY_CANNOT_ADOPT` / `OFFLINE_LATEST_UNSUPPORTED` / `CONFLICTING_CANDIDATE_OPTIONS` / `NOT_EXACT_VERSION` / `INVALID_LABEL` / `OUTPUT_ALREADY_EXISTS` / `INVALID_BUNDLE_PATH` / `PROBE_ENTRY_NOT_FOUND` / `INVALID_BUNDLE_MANIFEST` / `MIXED_PEER_BASELINE` / `BUNDLE_DIGEST_MISMATCH` / `PEER_UNSATISFIED` / `VERIFY_REQUIRED` 等失败关闭码。
- 分发合同（A→B）：B 的 `files` 含 `dist`；运行依赖 `@playwright/test` 精确 `1.65.0`（+ `vite 8.3.8`）；默认入口 `resolveDefaultProbeEntry()` 始终指向包内 `dist/probe/probe.mjs`（三种布局均验证，不依赖调用者 cwd / 仓库布局）；覆盖顺序 `--probe-entry` > `ZHINEXUS_ECHARTS_PROBE_ENTRY` > 默认；CLI **故意不暴露** `--font-digest`，故 `fontDigestSource` 恒为 `measured`。
- 安装包只读是硬约束：`checkOutputDirSafety()` 三判（不是文件系统根 / 符号链接、与任一源路径互不包含、可证明是本脚本产物）；只读边界从 `dist/probe` 扩大到整个已安装包；cwd 在包内时默认输出改道系统临时目录并留痕（`outputSubstituted` / `outputSubstitutionReason`）。
- `consumerSources[].integrity` 合同：字段集合固定 6 个，取值只能来自消费者 `package-lock.json` 记录、不从顶层候选声明抄；锁与 registry 不一致时带出锁里真值且 `verified:false`；核对跳过时为 `null`，不用顶层值填洞。
- 探针自身缺陷 vs SDK 缺陷：本轮共修掉 **7 + 12 + 3 + 1 = 23 处探针自身缺陷**（`--label` 覆盖、React TS17004、视觉基线误报 NEW、`mergeBaselineEvidence` 按框架去重、临时目录清理、`command` 缺 `probe.mjs`、`PROBE_DEPENDENCY`、`execFileSync` 外部工具链、`browserRevision` 硬编码、字体摘要未实测、`page.evaluate` 作用域、基线冲突 fail-closed、`summariseDimensions` 缺证据、integrity 闸门、未覆盖项硬编码 Linux、`frameworkVersion` 取声明值、`spawnSync` shell:true、自动 legacy、`rewritten` 作用域、`new URL('offline')`、脏消费者复制、`--font-digest` 覆盖不一致、空环境投影 TypeError、`getInstanceByDom` 的 Element/HTMLElement），**全部先红后绿，没有一条是 SDK 缺陷**。另一条判据：CLI 正确拒绝脏消费者并给出 `CANDIDATE_INTEGRITY_UNVERIFIED`，不是 CLI 缺陷。

**ECharts hold 的终态**

  - **`whenRendered()` 三个调用前提**（不能无条件当截图就绪信号，两侧实现相同）：① 控制器必须已建立（Vue `controller.value?.whenRendered() ?? Promise.resolve()`，React `controllerRef.current?.whenRendered() ?? Promise.resolve()`——控制器为 `null`（尚未挂载、已卸载）时**立即 resolve**，那不是渲染完成）；② 容器必须已有有效尺寸（挂载时零宽高或隐藏，SDK 不创建实例，等 `ResizeObserver` 拿到非零尺寸才初始化，这期间同样立即 resolve）；③ 渲染必须已触发（控制器刚建立时内部 `pendingRender` 也是已 resolve 的 promise，只有这次 `setOption` 触发的 `finished` 才唤醒等待者）。正确做法：客户端挂载后、容器有非零宽高时再调用；容器初始隐藏（折叠面板、Tab 页、`display:none`）时先等它可见再调用；SSR 阶段不要调用。示例页完整就绪协议（`window.__COMPONENT_EXAMPLE__` 的 `ready`/`states`/`runState`/`getChecks`）见 G1 回执，其做法（`document.fonts.ready` 后轮询系列 id 快照相对上一状态真正变化、超时即报错，**之后**才 `await whenRendered()`）值得照抄。
