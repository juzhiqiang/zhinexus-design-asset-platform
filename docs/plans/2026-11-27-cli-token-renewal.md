# JWT 两小时有效期与 CLI 活跃续签

用户于 2026-11-27 要求：令牌至少两小时有效，有操作时应在过期前续签。沿用自托管 ES256 JWT 和现有身份/ACL，不修改原架构文档。

## 范围与接口

- 在干净基线的 `fix/cli-token-renewal` 分支顺序实施，不修改用户组件项目或冻结发布材料。
- 自托管 access token 有效期 7200 秒；网页会话 Cookie 与实际已验证的令牌剩余寿命一致，不再写死 300 秒；授权尝试的五分钟窗口不变。
- 新增 `POST /v1/auth/oidc/renew`，无业务请求体；先完整认证仍有效的 Bearer JWT，再由同一本地 issuer 签发新令牌。响应契约 `renewTokenResponse` 为 `{ accessToken: string, expiresIn: number }`。保留身份、client、账号版本及原始 auth_time，角色采用服务端本次认证的有效角色。
- 不凭 Cookie 换出 Bearer JWT，不续签过期、停用、撤权或非本地 issuer 令牌，不保存密码。外部 OIDC 的时限仍由其 issuer 控制；不冒签外部令牌。
- CLI 在命令开始与后续平台请求前检查 JWT，剩余不足 300 秒且仍有效时续签；同进程并发合并续签。登录与续签共用跨进程凭据路径锁，在锁内重读，旧令牌仍匹配时才原子更新；显式或环境 Token 不会覆盖其他已保存登录，也不创建新登录。锁有限等待，未知锁不自动抢占；异常退出遗留的锁需用户确认无相关 CLI 操作后手动清理。
- 只向精确 API origin 的固定续签路径发请求，拒绝重定向。旧服务或不支持的 issuer 返回 404 时沿用仍有效的原令牌；401/403、网络及响应校验失败明确报错，保留原凭据。完全过期需重新登录。
- 发布创建/完成上传、提交作业、状态轮询及重试均使用当前令牌；不向预签名对象上传附带平台凭证。

## 重点回归

临界过期与已过期不同；续签保留 auth_time，不能复活强制退出的账号；Cookie 不得导出 JWT；不同 origin 不发凭证；外部 issuer 不由本地冒签；响应不合法或服务拒绝不得覆盖旧文件；长任务不固定使用初始令牌；预签名上传不夹带 Bearer。
